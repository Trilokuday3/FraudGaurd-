## Threshold selection

Cost matrix: false negative = transaction amount, review = $3.50 flat, false
positive (block) = $25 flat (see
`docs/superpowers/specs/2026-09-15-decision-engine-api-design.md` for the
full rationale).

Run against the real 519,876-row `./data/features.parquet` and the real
deployed run:

- `deployed_val_pr_auc` (written by `ml.enrich_deployed_run.enrich_deployed_run`): **0.5316211004945466**
  (notably lower than the run's `test_pr_auc` of 0.7100955151748024 — a real
  train/val-vs-test gap for the calibrated baseline, not a computation error;
  left as-is per this task's scope, flagged here for sub-project 3/5 follow-up).
- Note: thresholds are grid-searched on the same validation split the
  champion's calibrator was fit on (per spec, "never test") — this is an
  in-sample selection, a real caveat worth naming rather than glossing
  over, same as the illustrative cost matrix above.
- t_review: **0.04**
- t_block: **0.82**
- Total cost on validation at this policy: **34782.91**

(These threshold/cost numbers are numerically identical to the earlier

Cost curve (cost vs. `t_review`, at the optimal `t_block=0.82`) — a sample of
points evenly spaced across the real curve generated by

Cost is minimized right at the chosen `t_review=0.04` and climbs steeply on
either side. Recall `is_approve = scores < t_review`: dropping `t_review`
toward 0.0 shrinks the approve band to almost nothing, so almost every
transaction falls into the flat-fee review band and **review fees
dominate**; raising `t_review` toward `t_block` does the opposite — it
widens the approve band, so more transactions (including real fraud) get
waved through without review and **missed fraud (false negatives)
dominates** instead.

## Test suite

Run: `pytest tests/unit tests/features tests/dq tests/integration -v`
Result: `90 passed in 244.47s (0:04:04)`

An earlier version of this document (before Task 11 landed) reported a
test-isolation bug here: two tests failed only when the full suite ran
together, never in isolation. Root cause, found by running the full suite
before merge (not by a per-task review, which structurally can't see
cross-file test ordering effects): `mlflow.set_tracking_uri()` mutates the
real `os.environ["MLFLOW_TRACKING_URI"]` as a side effect, leaking a
tmp-path value from an unrelated earlier test into `Settings()`'s real-env
reads; separately, `serving/config.py`'s module-level settings singleton
wasn't being reloaded by the integration test fixture (only `serving.app`
was). Both fixed in commit `5b43750` — `monkeypatch.delenv(...)` guards the
unit test against OS-level leakage, and the fixture now reloads
`serving.config` before `serving.app`. The suite is genuinely green now,
verified by re-running it after the fix, not just trusting the fix's own
tests.
